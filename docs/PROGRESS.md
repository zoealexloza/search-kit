### Verified findings (tested in a scratch org, not assumed)

1. **SOSL binds:** `Search.query` resolves `:var` binds, but only to local variables with fixed names, so it can't bind a variable number of values. SOSL filter values are therefore validated literals.
2. **`INCLUDES` with binds:** `INCLUDES (:listVar)` fails ("Invalid bind expression type of List<String> for column of type String"). `INCLUDES (:p0, :p1)`, with one scalar bind per value, works, and so does `IN (:p0, :p1)`.
3. **Integer columns reject Decimal binds** ("Invalid bind expression type of Decimal for column of type Integer"). Whole-number fields get Integer/Long rule values, and `10.5` on an Integer field is rejected as invalid config.
4. **`instanceof` quirk:** a `Date` value is also `instanceof Datetime` (not the other way round), and Integer/Long values are `instanceof Decimal`. Type checks test `Date` before `Datetime`, and numbers convert through their string form instead of being cast.
5. **CMDT records in tests:** `DeveloperName`, `Id` and fields can be set in memory with a normal constructor. Metadata relationship fields are `Id`-typed in Apex, so they can't hold a DeveloperName: the deploy XML uses DeveloperNames, but runtime values are Ids. Config is joined on Id only.
6. **`Schema.describeSObjects`** throws `InvalidParameterValueException` for an unknown object name.
7. **Operator words as terms** (`AND`, `or`, `NOT`, `AND NOT`) don't make SOSL throw; they are simply searched. No special handling needed.
8. **Hidden standard fields in scratch orgs:** `Contact.DoNotCall` and `Contact.HasOptedOutOfEmail` are missing from the admin's describe field map, even though `Contact.DoNotCall` compiles. Tests use `Case.IsEscalated` as the checkbox field instead.
9. **AuraHandledException** can't be thrown from anonymous Apex ("Can only throw this exception type from VisualForce or Aura context"), so smoke scripts call `SearchService` directly for error cases.
10. **Code Analyzer needs Java 11+** for PMD, CPD and Graph Engine. Without Java it reports those engines as errors and runs only the regex, ESLint and retire-js engines, so it never checks the Apex. A JDK 21 is installed at `C:\Program Files\Microsoft\jdk-21.0.13.21-hotspot` but isn't on PATH. Set `JAVA_HOME` (or `engines.pmd.java_command`) before running it.

### Done

### Findings

1. **Knowledge works in a plain Developer scratch org** with the `Knowledge` feature and the two settings. The running user needs `UserPermissionsKnowledgeUser` to create articles. `KnowledgeSettings` metadata must list every language under `languages`, not only the new one; `defaultLanguage` is a top-level element.
2. **SOSL on `Knowledge__kav` without filters** returns only `Online` articles in the running user's language. That's a platform default, not something to rely on: an explicit `PublishStatus = 'Draft'` or `'Archived'` returns drafts and archived versions to a user who can see them.
3. **SOQL on `Knowledge__kav` has no implicit filter:** an internal user gets drafts, archived versions and every language. So browse mode (facets without a term, which uses SOQL) must always add the filters.
4. **Language:** with no `Language` filter, SOSL uses the user's language if it's an active Knowledge language, and otherwise the default Knowledge language: an `es` user gets Spanish, `fr` and `es_MX` users get English. A `Language` value that isn't an active Knowledge language **throws** ("Invalid language code"). The active languages are the `Language` picklist describe values. Describe doesn't mark the default language, and `KnowledgeSettings` can't be queried in Apex.
5. **`WITH DATA CATEGORY` applies to the whole SOSL query.** With another object in `RETURNING`, the query fails ("The category group name is not valid for the entities you are searching"). A semi-join on `Knowledge__DataCategorySelection` isn't allowed either ("can not be filtered in a query call"). So a Knowledge object with a category filter needs **its own SOSL query**. SOQL supports `WITH DATA CATEGORY` together with `WHERE`, `ORDER BY` and `LIMIT`.
6. **Category operators:** `BELOW x` includes `x` itself; `AT (a, b)` matches either category. Two conditions on the same group joined with `AND` must both match (in this data, nothing does). Names in the query take a `__c` suffix (`Products__c BELOW Nimbus_Cloud__c`).
7. **Category describe:** `Schema.describeDataCategoryGroups` and `describeDataCategoryGroupStructures` take `KnowledgeArticleVersion`, not `Knowledge__kav` (the error says so). They return **only what the running user can see.** The guest (visibility: Nimbus Cloud) gets Nimbus Cloud and Nimbus Mobile, but not their parent All. The customer (visibility: Stratus Desk) gets only Stratus Desk. A user with no visibility gets no groups.
8. **A category the running user can't see makes the query throw.** A group that isn't visible gives "The category group name is not valid…". A category that isn't visible gives "Invalid data category name"; that includes the parent of a visible category, e.g. `BELOW All` for the guest. So validating against the running user's describe gives exactly the categories that are safe to query.
9. **The platform enforces guest and customer visibility.** A guest with Read on Knowledge and category visibility, running SOQL with no filters at all, sees only `Online` articles with `IsVisibleInPkb`, in its visible categories or with no category, in **every language**. It never sees drafts, even a draft with the guest channel flag set. A customer user gets the same with `IsVisibleInCsp`. With Read but no category visibility, a user sees only articles that have no category.
10. **Channels:** new articles are visible in the internal app only (`IsVisibleInPkb` and `IsVisibleInCsp` false). The demo setup must set the channels before publishing.
11. **Category visibility for site users comes from the profile.** `categoryGroupVisibilities` in Profile metadata works for the guest profile and for a custom Customer Community profile. PermissionSet metadata has no such element (deploy error). The demo's custom `Support_Portal_Customer` profile can carry it. The guest profile is created with the site, so it needs a setup step, as guest access does today.

## 2026-11-24: Facet Values and collapsible filters

Owner requests from their Aura site: a Case Status facet offered all ~20 statuses (some only used by certain record types), and a long filter list should collapse like an accordion.

### Facet Values (data model change, owner approved)

- **New field `Search_Facet__mdt.Values__c`** (Text 255, subscriber controlled): optional allowlist of values to offer, API values separated by `;`, shown in that order; `true`/`false` for checkboxes. Blank offers every active value, as before. It narrows only the filter's choices, not the records found (a filter rule does that).
- **Validation (`SchemaValidator.parseFacetValues`):** each value must be an active picklist value (any case; canonical spelling kept); unknown ones are skipped and logged; repeats dropped. If none is valid the facet is skipped (logged) instead of silently offering everything.
- **`FacetService`:** offers only the configured values, in their order; visitor selections outside the list (e.g. an edited `f=` URL) are dropped like any invalid value. Filter rules on the same field still narrow the list.
- **Why Text (255), not Long Text Area (checked in `sskit`):** `getAll()` and `getInstance()` return a long text area value cut at 255 characters (a 400-character value came back as 255; SOQL returned all 400). Reading it with SOQL instead fails for visitors: a minimum-access user gets "sObject type 'Search_Facet__mdt' is not supported", and granting visitors read on the config types would expose the configuration. 255 characters fits a curated list of roughly 12–20 typical status values.
- **Record type:** not used. Apex describe has no per-record-type picklist values (only the UI API has them, via a callout guests can't make); the Values list covers the need.
- The field was first deployed to `sskit` as Long Text Area and replaced (a custom metadata field can't change type in place; removed with a destructive deploy).

### Collapsible filters

- **`searchFacets`:** every facet is its own disclosure (heading with a button, `aria-expanded` / `aria-controls`; heading level 3, or 4 under object headings). Open by default; a closed facet with selections shows the count ("Status (2 selected)", new label `Search_Facet_Heading_Count`). Values stay rendered while hidden, so selections are kept. The open/closed choices live in the panel component.
- **`searchResults`:** new Builder property **Collapse each filter** (`collapseFilters`, default off) starts every facet closed; a facet with a selection still starts open.
